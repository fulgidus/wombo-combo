---
title: Internationalisation (i18n)
description: How wombo-combo translates the CLI and TUI with i18next, how to pick a language, and how to add a new locale.
---

wombo-combo translates its terminal UI and human-readable CLI output with
[i18next](https://www.i18next.com/). English (`en`) is the source of truth;
Italian (`it`) ships as a complete second locale.

## Choosing a language

The locale is resolved in this order, first match wins:

1. `tui.locale` in `.wombo-combo/config.json` (anything other than `auto`)
2. the `WOMBO_LOCALE` environment variable
3. `LC_ALL`, `LC_MESSAGES`, then `LANG`
4. `en`

Values such as `it_IT.UTF-8` or `pt-BR` are normalised to a shipped locale
(`it`, or `pt` if it existed); unsupported values are ignored. In the TUI,
**Settings → Locale** cycles through `auto` and every shipped locale.

```sh
WOMBO_LOCALE=it bun dev tasks list
```

Machine-readable output (`-o json`, `-o toon`) is **never translated**: field
names, enum values and messages stay English so scripts and agents see a
stable contract.

## Architecture

| Piece | Location |
| --- | --- |
| Core (detection, `t()`, plurals, fallbacks) | `src/lib/i18n.ts` |
| Ink helpers (`useI18n()`, `getLocaleT()`) | `src/ink/i18n.ts` |
| Locale registry | `src/locales/index.ts` |
| Resources | `src/locales/<lng>/tui.json`, `src/locales/<lng>/cli.json` |

Resources are statically imported JSON, so Bun, `bun build` and `tsc` inline
them (no runtime file access). Keys are **flat dotted strings**
(`"cli.tasks.add.added"`, not nested objects). The two files per locale are
merged into one resource: `tui.json` holds screen text, `cli.json` holds
command output.

Missing keys fall back to English. In dev mode (`WOMBO_DEV=1` or
`WOMBO_I18N_DEBUG=1`) each miss is reported once on stderr and recorded; read
them with `getMissingKeys()`.

## Writing translatable code

```ts
import { t, msg } from "../lib/i18n";

console.log(t("cli.tasks.add.added", { id, title }));        // interpolation
console.log(t("cli.tasks.archive.done", { count: n }));      // plural
const m = msg("cli.foo", { id });                            // deferred; rendered later
```

In Ink components use the hook so the active locale applies:

```tsx
const t = useI18n();
return <Text>{t("fakeTask.field.tasks")}</Text>;
```

Module-level helpers take a `t: TFunction` parameter (defaulting to the global
`t`) instead of reading translated constants. When a constant must stay English
for backward compatibility, build it with `getLocaleT("en")`.

Rules:

- **Key naming:** `<area>.<screen or command>.<thing>`, camelCase segments.
- **Interpolation:** `{{name}}`. Never concatenate translated fragments;
  word order differs between languages.
- **Plurals:** provide `key_one` and `key_other` and pass `{ count }`.
  Languages with more CLDR categories need them too (Italian also needs
  `key_many`, used for large numbers such as 1 000 000).
- **Never key logic off translated text.** Use stable ids (for example a
  field's `id`), not the label shown to the user.
- **Do not translate** command names, flags, paths, config keys, task/quest
  ids, enum values or anything written to files and JSON output.

## Adding a locale

1. Copy `src/locales/en/tui.json` and `cli.json` to `src/locales/<lng>/`.
2. Translate the values. Keep every key, every `{{placeholder}}`, and the
   leading/trailing spaces. Add the extra plural forms your language needs.
   For prompts whose answers are parsed (`preflight.console.yesAnswers`),
   list the answers your language accepts.
3. Import both files in `src/locales/index.ts` and add the locale to
   `RESOURCES`:

   ```ts
   export const RESOURCES = {
     en: merge(enTui, enCli),
     it: merge(itTui, itCli),
     de: merge(deTui, deCli),
   };
   ```

4. Run the checks below. `AVAILABLE_LOCALES`, locale detection and the
   Settings screen pick the new locale up automatically.

## Checks

```sh
bun test tests/i18n-keys.test.ts   # keys used in code exist; locale parity; plural forms; placeholders
bun test tests/i18n-it.test.ts     # shipped Italian locale: completeness and switching
```

`tests/i18n-keys.test.ts` scans static `t("literal.key")` calls, so keep keys
literal where you can; dynamically built keys (``t(`x.${id}`)``) are not
checked and need their own test.
